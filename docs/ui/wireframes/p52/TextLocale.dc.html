P52 — Text Expansion, Line-Height and Localization

Prompt 52 · Phase 5 · Depends on Prompt 45 — button expansion rules, script line-height variance, number/date/currency per UI-UX §128–131
Target locales: English (en-IN), Hindi (hi-IN), Marathi (mr-IN), Tamil (ta-IN), Telugu (te-IN), Kannada (kn-IN). Sample strings below are real translations, not Lorem text. All expansion figures measured against English baseline. Hindi is the primary Indic locale for expansion testing.

Button and Label Expansion Rules (UI-UX §128)

Rule 1 — Buttons grow; they never truncate
A button label must always be fully visible. Buttons have min-height: 48dp and padding: 12dp 20dp horizontal. When a translated label exceeds the button's natural single-line width:
  • Full-width buttons (most primary CTAs): grow in height by wrapping to 2 lines. Max 2 lines — if a translation cannot fit in 2 lines at 13sp, escalate to the translation team for a shorter string.
  • Auto-width buttons (dialog action buttons, inline): grow in width. If they would overflow the container, switch to stacked layout (primary above, secondary below).
Never: ellipsis ("Add Sa…"), clip, or reduce font size below 12sp for a button label.
Always: wrap to 2 lines, or stack buttons, or request a shorter translation.

Rule 2 — List labels and nav labels: truncate at 1 line with ellipsis only
List row primary text (--type-body-lg), navigation labels (--type-label), and chip text (--type-label-lg) use single-line ellipsis truncation when the translation overflows. These are read in context — the surrounding UI provides disambiguation. Exception: customer/supplier names on detail screens (title size) must never truncate — use 2 lines if needed. Navigation tab labels should be kept to ≤6 characters per locale; flag any translation that exceeds this.
Rule 3 — Dynamic layout response for Indic scripts
Hindi and Marathi translations typically run 60–90% longer in glyph count than English, but rendered glyph width in Noto Sans Devanagari at equivalent point size is usually 80–120% of Inter at the same size. Net visual expansion: +30–50% for most labels.

Tamil, Telugu, Kannada scripts have complex ligatures — at 11sp (--type-label), some glyphs may touch. Set lineHeight to the Indic value from P45 even at label sizes. Never set a fixed pixel height on a text container — always use flex or min-height.

Number, Date and Currency Localization (UI-UX §129–131)

Currency — Rupee formatting
Use Intl.NumberFormat with locale-appropriate grouping. Indian numbering system uses lakh/crore groupings (2-2-3 from right), not 3-3-3.

All locales48,200₹48,200Under 1 lakh: standard 3-digit grouping (same for all Indian locales)
Abbreviated display (MetricCard, KPI chips): Values ≥ 1 lakh → "₹1.25L"; ≥ 10 lakh → "₹12.5L"; ≥ 1 crore → "₹1.2Cr". Never abbreviate in transaction detail or invoice views.
Number formatting — quantities and percentages
  • Stock quantities: Always integer, no decimal. "240 units" not "240.0 units". Locale: en-IN integer formatting.
  • Percentages: One decimal place max. "12.5%" in en-IN. In hi-IN: "12.5%". Percentage sign is always Latin "%" — do not localize.
  • GST rate: "18%" — never "18.00%". Fixed decimal format where the rate is always whole.
  • Negative values: Show with "−" (minus sign U+2212), not "(" parenthesis. Always red (--color-error) for financial negatives.

Digit rendering (UI-UX §131)
Always render digits in Latin (ASCII) numerals 0–9 for all locales, including hi-IN and mr-IN. Devanagari numerals (०–९) are not used in this app — financial data must be universally scannable by users of any script literacy level. Tested: Noto Sans Devanagari renders Latin digits correctly at all weights.
